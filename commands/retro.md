# /cmux-team:retro

直近 N 件のクローズ/アボートタスクのサマリーを読み、繰り返しパターン・設計問題・
ロールプロンプトの改善余地を分析してレポートする。

## 引数

`$ARGUMENTS` に件数を指定する（例: `10`）。省略時は 10 件。

## 手順

### 1. タスク状態を取得

```bash
cat .team/task-state.json
```

`status` が `closed` または `aborted` のエントリを `updated_at` の降順で最大 N 件抽出する。
N 件に満たない場合はあるだけ処理する。

### 2. 各タスクの詳細を読み込む

対象タスクの ID ごとに:

```bash
ls .team/tasks/ | grep "^<id>"
```

ファイルが見つかれば `Read` で開いて title・body を取得する。
`task-state.json` エントリの `journal` フィールド（完了/中止サマリー）も取得する。

### 3. パターン分析

収集した情報をもとに以下の観点で分析する。各観点で具体的なタスク ID を挙げること。

#### 観点 A: 繰り返しパターン

- 同じエラーや操作で複数回失敗・abort しているケースがあるか
- 毎回同じ手順を踏んでいる工程（自己解決しているが毎回コストがかかる）
- worktree conflict・API rate limit・trust 確認・sync check 失敗 等の頻度

#### 観点 B: 設計・実装方針

- 同一ファイルやモジュールへの修正が短期間に集中しているか
- Conductor 間で実装方針が揺れているか（直前の変更を即座に覆す修正）
- テストが壊れる・テストなしの修正が繰り返されているか

#### 観点 C: ロール・プロンプト・CLAUDE.md

- CLAUDE.md のガードレール（禁止行動）が無視されているケース
- Conductor/Agent が「ユーザーに進捗報告した」「直接 cmux send した」等の逸脱行動
- エージェントが迷いやすかった領域（判断基準が不明確な場面）
- テンプレートの指示が曖昧で誤解が生じたケース

#### 観点 D: その他

上記に当てはまらないが気になった点。

### 4. レポート出力

以下の形式でまとめる。パターンが見つからなかった観点は省略してよい。

---

## Retro レポート（直近 N 件 / 対象: `closed` + `aborted`）

### A. 繰り返しパターン

（発見した問題と具体的なタスク ID、推奨アクション）

### B. 設計・実装方針

（発見した問題と具体的なタスク ID、推奨アクション）

### C. ロール・プロンプト・CLAUDE.md

（改善が推奨される箇所と具体的な修正案）

### D. その他

（気になった点）

---

**分析対象タスク:** T___ / T___ / ...（実際に読んだタスク ID を列挙）

---

パターンが全く見つからない場合は「直近 N 件のタスクに特筆すべきパターンは見つかりませんでした」と表示する。
