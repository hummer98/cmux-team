## 概要

cmux-team の本質的な価値命題を言語化したセッション。「AI観察箱」というコンセプトと、それが既存オーケストレーションツールと何が違うのかを整理した。

---

## 解いている問い

AutoClaude・Claude Code Agent Teams・Devin などの既存ツールでは、どんな役割のどれだけのエージェントが何の問題に向き合っているかが **ブラックボックス** になる。

この弊害は「不安」という感情として現れる。全作業を微細に監督したいわけではないが、中間生成物を斜め読みしたりタスクのサマリーをちらっと見るだけで「まずいことが起きているか」がわかる状態が必要。

リアルタイムの異常検出ができると、改善プロセス（プロンプト・設計・アーキテクチャの修正）を早く回せる。最終結果だけでは、このプロセス改善において人間が理解できる情報が限定的になる。

---

## 要件

### コアコンセプト：「AI観察箱」

> **ブラックボックスではなく、AI の振る舞いをリアルタイムに観察できる箱**

既存ツールとの対比：

| | 自動化ツール（AutoClaude 等） | AI観察箱（cmux-team） |
|--|--|--|
| 設計思想 | プロセスを隠して認知負荷を下げる | プロセスを見やすくして認知負荷を下げる |
| 観察粒度 | 結果（result）ベース | 進行中（on-go）ベース |
| 人間の役割 | 指示と結果確認 | 異常の早期検出と改善サイクルの入力 |
| AI への期待 | 正しく動く前提 | 間違う前提で構造を作る |

### UX 要件

1. **読みたい時にすぐ読める（探さないで良い）**
   - ログが存在するだけでは不十分。どこを見ればいいかがすぐわかること
   - 探索コストがゼロに近い状態

2. **動作要約がある（summary.md 的なもの）**
   - タスクごとに、スキマブルな粒度で自動生成される要約
   - 30秒以内に「今何が起きているか」が把握できる

3. **異常が目立つ**
   - 現状は「見えている」だけで「まずいことが目立つ」設計にはなっていない
   - 正常な進行と異常な進行が視覚的に区別できること

### 観察の層ごとの充足状況（2026-04-28 時点）

| 層 | 問い | 現状 | 充足度 |
|----|------|------|--------|
| メトリクス | 今何が起きているか | TUI タスク一覧・Conductor ステータス | △ |
| ログ | 何が起きたか | manager.log, trace DB | △ 探す必要あり |
| トレース | なぜそうなったか | `trace-task` コマンド | △ コマンドを知らないと辿り着けない |
| **要約** | **何をやっていたかのナラティブ** | **なし** | **✗** |

---

## 制約

- 「すべてのログを読む」ことは目的ではない。人間は **周辺注意（peripheral attention）** で異常を検出する
- 観察とは凝視ではない。斜め読みできる構造と、読みたい時に読める配置が重要
- マルチステップのAIエージェント群を組み上げる開発プロセス自体にも、個々のエージェントの on-go 観察が必要（結果ベースの改善では情報が不足する）

## 未決事項

- `summary.md` 的な要約を**誰が・いつ・どの粒度で**生成するか
  - Conductor が完了時に自動生成？
  - Manager が定期的に集約？
  - Agent が中間報告として書く？
- 「まずい」の定義をどこまで自動検出できるか（vs. 人間の目に委ねるか）
- 人間が観察した結果を改善ループにどう戻す仕組みにするか（現状は暗黙）
